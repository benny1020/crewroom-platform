# 실사용 준비와 안정 버전 마일스톤

2026-10-19 기준. 현재 릴리스는 0.10.0이다. 목표는 여러 구성원이 같은 서버의 에이전트·스킬·기억·업무 결과를 이어서 사용하는 것이다. 설치마다 독립 워크스페이스 하나와 운영자가 선택한 모델 endpoint·저장소를 기준으로 한다.

완료는 구현과 해당 단계의 검증 증거를 모두 갖춘 상태다. 자동 검사 통과, 실제 모델 검증, 구성원의 사용 결과를 구분한다. 아래 수량은 앞으로 수행할 검증의 최소 범위이며 달성한 성능 수치가 아니다. 일정은 endpoint·테스트 프로젝트·참여자 준비 후 정한다.

| 단계 | 목표                         | 현재 상태                                | 완료 판단                                                            |
| ---- | ---------------------------- | ---------------------------------------- | -------------------------------------------------------------------- |
| M0   | 공용 에이전트 플랫폼 기반    | 완료                                     | 협업·기억·스킬·실행·복원 구현, 자동 검사 156개와 CI 성공             |
| M1   | 실제 모델과 기억 품질 검증   | 준비 도구 구현 · 실제 endpoint 검증 대기 | 실제 모델의 검토·개발·QA 흐름과 출처 회상을 검증                     |
| M2   | 실제 서버 UX 정리            | 주요 흐름 개선 · 일부 공통화/검증 남음   | 요청부터 결과 수용까지 일관된 화면으로 사용, 데모와 서버의 중복 축소 |

0.9.0에서 서버 오피스의 동료 선택·스킬 바로 요청·적용 버전 완료 기준, 업무 필터, 팀장 운영 현황을 구현했다. 데모/서버의 캐릭터 업무 자리 컴포넌트를 공유한다. 한국어 합성 답변 20문항과 호출 예산·동일 조건 비교 도구, 실제 PostgreSQL 큐 10건/동시 2개 회귀도 추가했다. [검증 기록](SERVER_VERIFICATION.md) · [답변 평가](ANSWER_EVALUATION.md). 실제 endpoint/실사용 검증을 대체하지 않으므로 M1~M4는 열어 둔다.

0.10.0은 분석·개발 스킬 요청을 맞는 입력 경로로 연결하고, 결과 중심 업무방·인계 카드·같은 단계 결과 비교·수동 질문함을 추가했다. 재작업 지시와 저장한 답변은 읽기 전용·native 코드 실행 양쪽의 새 입력에 고정된다. 새 답변이 빠진 옛 결과의 수용·인계를 막는다. [구현 계약과 화면](WORKFLOW_IMPROVEMENTS.md). 역할별 결과 스키마·자동 질문·전체 데모/서버 공통화·실제 모델 효용은 남아 있다.

0.11.0은 긴 대화의 페이지·원문 검색과 초안 보존, 검색 투영 인덱스, 종료 Job 지연 로딩, 로그 회전·운영 통계를 추가했다. 업무 10만 건·한 방의 메시지 100만 개를 별도 DB에서 측정했다. [장기 운영과 남은 운영 경계](LONG_TERM_OPERATIONS.md). PITR·ANN·HA·실제 서버의 운영 SLO와 실제 모델 품질은 아직 완료로 판정하지 않는다.

M1과 M2는 병행할 수 있다. M1의 연결 준비를 기다리는 동안 M2를 진행한다. M4의 부하·복구 준비도 먼저 수행할 수 있지만, 안정 버전 판정에는 M3의 실제 사용 결과가 필요하다.

## M0 · 기반 구현 — 완료

- 공용·개인 에이전트, 팀장·팀원 권한, 공유 업무방과 책임 인계.
- 에이전트별 기억, 출처·정정·적용 기간·권한 검사, 스킬 게시와 실행 버전 고정.
- PostgreSQL 영속 상태·Worker 큐·Docker 개발 작업과 별도 QA, 사람의 결과 수용.
- 암호화 백업·복원, 비밀 파일 권한 검사, 자동 검사 156개.

근거: [구현·검증 기록](SERVER_VERIFICATION.md), [Astra 기억·실행 리뷰](ASTRA_MEMORY_REVIEW.md), [기반 커밋 CI](https://github.com/benny1020/crewroom-platform/actions/runs/39095867271). 실제 모델의 업무 능력과 운영 배포의 효용은 M1·M3에서 검증한다.

## M1 · 실제 모델과 기억 품질

담당: 구현 담당자와 endpoint·테스트 프로젝트를 준비하는 운영 담당자.

선행 조건은 사용할 모델·인증 설정, 호출 비용 상한, 검증용 저장소와 프로젝트 실행 이미지다. 의미 검색을 사용할 배포는 embedding 연결도 준비한다. 설정은 [연결 안내](CONFIGURATION.md), 실행 이미지는 [실행 구조](CODE_EXECUTION.md)를 따른다.

- [ ] 실제 모델로 읽기 전용 검토, 작은 코드 수정, 정확한 patch의 별도 QA를 각각 두 번 이상 완료한다.
- [ ] 결과마다 대상 SHA·스킬 버전·모델 식별자·사용량·지연·실제 검사 로그·사람의 수용/재작업 판단을 남긴다. 제공자가 사용량을 반환하지 않으면 비용을 미측정으로 표시한다.
- [ ] 고정된 한국어 기억 사례 20개를 준비한다. **검색 회귀와 별도로 제공 문맥 기반 답변 사례 20개·평가 도구는 구현했다.** 오래된 기록, 표현이 다른 질문, 정정·삭제·만료된 출처, 개인·부서·에이전트 경계, 답이 없는 질문을 포함한다.
- [ ] 같은 원문과 문맥 예산으로 필요한 출처 회수, 답변 근거, 모름 응답, 낡은 사실 사용, 금지 정보 노출을 평가한다. 의미 검색 사용 여부도 기록한다.
- [ ] 인증 실패·429·시간 초과·잘못된 JSON·모델 호출 중 취소가 명시적으로 처리되고, 실패를 완료로 표시하지 않는지 확인한다.

완료 기준: 위 실행 증거와 사례별 판정이 있고, 경계 위반·실행하지 않은 검사의 성공 표시·잘못된 대상 결과 수용 같은 차단 결함이 없다. 정확도·비용·지연의 허용 범위는 검증 전에 업무 담당자가 정하고, 그 범위를 충족해야 한다. 작은 표본 결과를 일반 성능으로 확대하지 않는다.

## M2 · 실제 서버 UX 정리

담당: 제품·프런트엔드 구현 담당자. M1과 병행한다.

- [x] 오피스 → 에이전트·스킬 선택 → 요청 → 진행 상태 → 결과·근거 → QA·수용을 하나의 흐름으로 연결한다.
- [x] 적용 스킬의 필수 대상·버전·완료 기준을 요청 화면에서 확인하고 실행한다. 코드 검증은 기존 개발 결과의 인계로 연결한다. 사용자 정의 스킬별 동적 양식·역할별 결과 스키마는 후속 범위다.
- [x] 대기·실행·입력 요청·실패·재개 상태와 캐릭터 모션을 실제 서버 상태에 연결한다. 모션을 꺼도 같은 상태를 알 수 있게 한다.
- [x] 팀원에게는 이어갈 업무·확인 요청, 팀장에게는 담당·큐·실패·설정 문제를 우선 표시한다.
- [ ] 데모와 서버에서 재사용할 오피스·에이전트·상태 표시를 공통화하고, 데이터 연결 차이는 별도로 처리한다. 0.9.0은 캐릭터 업무 자리·상태 표시를 공유했다. 전체 화면과 공통 시나리오 정리는 남았다.
- [x] 1440·1280·1024px, 키보드 조작, 두 계정의 책임 인계, 새로고침·재접속을 실제 서버에서 확인한다. 모델 응답은 결정적 fixture이며 실제 endpoint 검증과 구분한다.

완료 기준: 두 구성원이 서버 화면에서 업무를 요청·인계·수용하고, 현재 상태와 다음 행동을 확인할 수 있다. 공개 데모와 서버의 주요 흐름을 같은 브라우저 시나리오로 검증하고, fixture 검증과 실제 모델 실행을 구분한다.

## M3 · 공동 사용과 효용

담당: 운영 담당자, 업무 책임자, 실제 사용자 3~5명. M1·M2 완료 후 한 프로젝트에서 약 1주간 관찰한다.

- [ ] 실제 업무 10건을 요청부터 수용 또는 재작업 판단까지 수행한다. 실패·취소한 업무도 기록에서 제외하지 않는다.
- [ ] 두 명 이상이 같은 업무방을 이어받고, 개발 → 리뷰 → QA 중 필요한 인계를 완료한다.
- [ ] 반복 업무 두 종류를 공용 스킬로 게시하고, 처음 작성하지 않은 구성원이 다시 사용한다.
- [ ] 각 업무에서 입력 준비·검토·수정에 쓴 사람 시간, 재설명 횟수, 결과 오류, 비용·지연을 기록한다.
- [ ] 비교할 기존 업무 사례와 기록 방법을 시작 전에 정한다. 관찰하지 않은 시간 절감률을 만들지 않는다.
- [ ] 실제 사용 중 발견한 요청 양식·기억·결과 형식·복구의 불편을 우선순위에 따라 수정하고 재확인한다.

완료 기준: 권한과 결과 증거의 차단 결함이 없고, 담당자가 수용한 반복 업무·공용 스킬 사례가 있다. 비교 가능한 업무에서 사람의 준비·검토·재작업 시간이 줄고 인계가 쉬워졌는지 확인한다. 효용이 확인되지 않으면 원인을 수정하고 해당 범위를 다시 검증한 뒤 확대한다.

## M4 · 운영과 안정 버전

담당: 운영·백엔드·QA 담당자. M3에서 확인한 사용 범위로 판단한다.

- [ ] 동시 실행 2개와 대기 요청 10개의 고정 시나리오에서 대기 시간·응답 지연·메모리·DB 부하를 기록한다. 현재 지원 한도와 운영자가 정한 허용 범위를 확인한다. **PostgreSQL 합성 큐 회귀로 10건을 2개씩 처리하고 중복 결과 0건을 확인했다. 실제 모델·호스트 자원 부하 측정은 남았다.**
- [ ] Worker 종료, Runner 재시작, 모델 응답 불명, DB 재시작을 확인하고 중복 발송·늦은 결과·잘못된 성공 처리가 없는지 검사한다.
- [ ] 대상 운영 환경에서 백업을 별도 환경에 복원하고 데이터·파일 hash·계정 세션·미완료 실행을 확인한다. 실제 복원 시간과 데이터 손실 범위를 기록한다.
- [ ] 업그레이드 전 백업, migration 실패 대응, 이전 릴리스 복구를 재현한다.
- [ ] 실패·대기열·heartbeat·저장 공간을 운영자가 확인하고 대응할 수 있게 한다. 보존 기간·비용·자원 한도와 담당자를 정한다.
- [ ] M1·M3 결과, 남은 제약, 실행 가능한 설치·운영·복구 안내를 릴리스 문서에 반영한다.

완료 기준: 정한 운영 범위에서 차단 결함이 없고, 운영 담당자가 복원·장애 대응을 재현할 수 있다. 지원하지 않는 사용량이나 환경까지 안정성을 보장하지 않는다. 이 기준을 충족한 범위를 안정 버전으로 공개한다.

## 진행 관리

[GitHub 마일스톤](https://github.com/benny1020/crewroom-platform/milestones)에서 단계별 상태를 관리한다. M0 이후 단계는 위 체크 항목과 증거가 갖춰졌을 때 닫는다. 외부 연결이나 실제 참여자가 필요한 항목은 준비 상태를 표시하고, 완료로 대신 처리하지 않는다.

공개 문서에는 재현 방법과 검증 범위를 남긴다. 원본 업무·대화·연결 설정·자격증명은 해당 배포의 권한 범위에서 관리한다. 시작 순서와 운영 절차는 [시범 운영 가이드](PILOT_GUIDE.md)를 따른다.
