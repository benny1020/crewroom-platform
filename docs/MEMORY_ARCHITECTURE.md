# 크루룸 — 에이전트별 장기 기억 설계

조사·반영일: 2026-10-15. 프레임워크 선정 재검토: 2026-10-16. 범위: 데스크톱 인터랙티브 목업과 실제 서버 구현을 위한 설계. 이후 웹 목업을 GitHub Pages에 정적 배포했으며, 실제 모델 호출·메모리 서버는 연결하지 않았다.

후속 웹 프로토타입의 대화별 개인 기억, 정정·삭제와 로컬 복원은 [반영 내역](IMPLEMENTATION.md)에 정리했다. 현재 검색 알고리즘과 코드별 동작은 [기술스택·아키텍처](ARCHITECTURE.md)에 있다. 이 문서의 서버 구조는 구현 제안이다.

실행기는 미선정이다. 기존 LangGraph 기본 추천은 비교 근거가 충분하지 않아 철회했다. 2026-10-16의 [공개 코드 상세 조사](OPEN_SOURCE_CODE_RESEARCH.md)에서 Paperclip 기반 업무 제어와 교체 가능한 하네스의 검증을 우선하도록 수정했다. 아래 기억·접근 범위·출처·정정 설계는 실행기와 분리해 유지한다.

## 제품에서 말하는 “계속 기억”

에이전트의 정체성과 기억은 대화방이나 실행 프로세스보다 오래 유지한다. 대화·작업 원문을 보관하고, 정리한 지식과 경험을 검색해 다음 업무에 사용한다. 저장소는 필요에 따라 확장하되, 모델의 입력 크기와 검색 정확도에는 한계가 있다. 모든 과거 사실을 언제나 완벽하게 떠올린다고 약속하지 않는다.

캐릭터·이름·모델·하네스 변경은 안정적인 `agent_id`를 바꾸지 않는다. 대화를 새로 열거나 서버 작업자를 재시작해도 같은 에이전트의 기억을 이어간다. 팀원이 보는 공용 대화와 개인 비서의 대화는 각각의 공개 범위를 유지한다.

제품의 주목표는 [서버에 상주하는 공용 에이전트의 공동 사용](SHARED_AGENTS.md)이다. 공용 에이전트의 기억은 사용자마다 복제하지 않고, 같은 Agent ID에 권한과 출처를 유지해 축적한다. 개인 비서의 기억은 별도 소유 범위로 두는 보조 기능이다.

## 오픈소스 선택과 프레임워크

- [LangGraph](https://github.com/langchain-ai/langgraph): 업무 단계, 대기, 재개, 인계를 구현할 때 적합하다. 장기 기억을 자동으로 완성해주는 것은 아니며 저장·검색·정정 정책은 서비스가 구현한다. LangChain 전체 도입은 필수가 아니다.
- [Letta 현재 소스](https://github.com/letta-ai/letta-code): 정체성과 기억을 유지하는 에이전트, 공유 기억을 참고할 후보. 2026-10-15 확인 시 [기존 letta 저장소](https://github.com/letta-ai/letta)는 현재 개발 소스로 `letta-code`를 안내하며 V1 서버는 archive로 분리돼 있었다. 오래된 V1 예제를 그대로 시작점으로 삼지 않는다.
- [Letta V1 기억 개념](https://docs.letta.com/v1-sdk/concepts/stateful-agents): 핵심 메모리 블록과 입력에서 빠진 메시지를 보관·검색하는 개념, 공유 블록을 참고했다. 이 문서는 legacy 경로이며 현재 SDK 사용법으로 간주하지 않는다.

제품의 장기 기억은 **별도 Memory Service + PostgreSQL + 원문 저장소**를 중심으로 설계한다. 실행기는 확정하지 않는다. 현재는 Paperclip의 조직·업무·실행 관리와 기존 Hermes 어댑터를 격리 환경에서 우선 검증한다. Letta Code의 에이전트별 기억 경로·변경 통합을 비교하고, Mastra·LangGraph는 남은 실행 요구가 구체화될 때 검증한다. 여러 실행기나 기억 엔진을 처음부터 중첩하지 않는다. 지금 목업에 이 패키지들을 설치하거나 연결하지는 않았다. 소스의 줄 단위 근거와 채택 조건은 [공개 코드 상세 조사](OPEN_SOURCE_CODE_RESEARCH.md)에 있다.

## 기억의 여섯 층

| 층 | 보관하는 것 | 읽는 시점 |
| --- | --- | --- |
| 원문 기록 | 대화 메시지, 사용자 지시, 관찰 가능한 도구 결과, 산출물 참조 | 출처 확인 또는 상세 검색 |
| 사실·선호·결정 | 보고 방식, 환경, 합의, 유효 기간이 있는 규칙 | 관련 업무를 시작할 때 |
| 업무 경험 | 해결한 이슈, 원인, 변경, 검증 결과, 실패와 회복 | 비슷한 업무를 만났을 때 |
| 업무 절차 | 반복 작업 방법, 성공 기준, 필요한 입력 | 스킬 후보를 만들거나 실행할 때 |
| 목표·미완료 약속 | 할 일, 담당, 마감, 대기 이유 | 재개·후속 작업을 결정할 때 |
| 현재 작업 맥락 | 최근 메시지, 작업 요약, 도구 상태, 다음 단계 | 해당 실행의 체크포인트에서 |

완료·취소 상태의 권위 있는 원본은 작업 저장소다. 기억에 남은 오래된 “진행 중” 문구로 작업을 다시 실행하지 않는다. 기억 검색 결과는 데이터이며 실행 권한을 새로 부여하지 않는다.

## 네 가지 보관 범위

```text
workspace/{workspace_id}/team
workspace/{workspace_id}/department/{department_id}
workspace/{workspace_id}/agent/{agent_id}
workspace/{workspace_id}/user/{user_id}/assistant/{assistant_id}
```

공용 에이전트는 자기 기억 + 소속 부서 기억 + 허용된 팀 기억을 참고한다. 개인 비서는 자기 소유자의 기억과 허용된 팀 기억을 참고한다. 개인 비서가 다른 사람의 개인 기억이나 모든 부서의 내부 기억을 자동으로 읽지 않는다. 실제 열람 권한은 workspace membership과 문서 ACL로 결정한다.

범위 유형과 식별자를 함께 비교한다. 예를 들어 QA 부서의 `department/qa`와 린의 `agent/qa`는 서로 다른 저장 공간이다. 모양·이름·소속 변경도 과거 기록의 공개 범위를 자동으로 확대하지 않는다. 팀 공개로 전환할 때는 새 공개본을 만들고 개인 원문의 민감한 내용을 제외한다.

## 서버 구성 제안

```text
웹 UI / API
  ├─ Identity & ACL ── agent_id / 사용자 / 부서 / workspace
  ├─ Conversation & Task Service ── 원문 메시지 / 작업 / 결과
  ├─ Agent Runner (교체 가능한 어댑터) ── 재개 체크포인트 / 하네스 / 도구
  └─ Memory Service
       ├─ PostgreSQL ── 기억 항목 / 버전 / 권한 / 출처 / 삭제 기록
       ├─ 전문 검색 + pgvector ── 허용된 범위의 검색 색인
       ├─ 객체 저장소 ── 큰 원문 / 첨부 / 산출물
       └─ 정리 작업자 ── 후보 추출 / 중복 병합 / 요약 / 재색인
```

이는 구현 제안이다. 실제 부하를 확인한 뒤 저장소·색인 용량을 확장한다. 작은 MVP부터 별도 검색 클러스터나 지식 그래프가 필요한 것은 아니다.

첫 운영 서버에서는 원문·산출물·불변 스킬의 파일 저장을 같은 서버의 영속 디스크 어댑터로 시작하는 배포안을 둔다. 위 객체 저장소는 이후 이행 가능한 저장 책임을 나타낸다. DB와 파일을 함께 백업·복원하고 실제 배포 상태는 [서버 운영 설계](DEPLOYMENT.md)와 구분해 확인한다.

서버는 **공용 Agent별 영속 ID·기억·작업공간·스킬·작업 큐**를 유지하고 팀원의 웹 접속과 무관하게 실행을 관리한다. 실행할 때 업무별 환경을 배정하고 완료·대기 시 상태를 저장한다. 개인 비서를 사용하는 경우 소유자별 ID와 저장 범위를 별도로 유지한다. 별도의 컴퓨터 환경이 필요한 업무에는 전용 실행 환경을 연결한다.

기억 항목의 기본 필드:

```text
memory_id, workspace_id, scope_type, scope_id, kind,
title, content, source_refs[], observed_at, valid_from, valid_until,
version, supersedes, status, author, confirmation, sensitivity,
task_id, skill_id, embedding_version, content_hash
```

## 쓰기·검색·정정 흐름

1. 메시지·작업 이벤트를 고유 event_id로 원문에 저장하고 outbox에 기록한다.
2. “기억해줘”처럼 명시한 내용은 해당 에이전트 범위에 저장한다. 자동 추출한 내용은 원문과 함께 후보로 만들며, 추론을 사용자 확정 사실로 표시하지 않는다.
3. 정리 작업자가 출처·범위를 유지한 채 중복을 합치고 새 버전을 기록한다. 같은 이벤트의 재처리는 중복 기억을 만들지 않도록 한다.
4. 질문 시 검색 **전에** 조직·사용자·에이전트·문서 권한과 유효 상태로 필터링한다. 정확 검색과 의미 검색을 결합하고 관련성·최신성·확정 여부를 고려한다.
5. 핵심 기억, 현재 작업, 검색된 기억과 필요한 원문만 입력 예산 안에서 선택한다. 인용에는 memory_id·version·source_ref를 남긴다. 충돌하는 결정은 최신 유효 버전과 시점을 확인한다.
6. 내용 정정은 기존 버전을 덮지 않고 후속 버전을 만든다. 검색은 기본적으로 현재 유효 버전을 사용하고 과거 시점 질문만 이전 버전을 사용한다.
7. 기억 삭제는 검색에서 즉시 제외하고, 파생 요약·색인·캐시까지 제거를 전파한다. 원문 대화 삭제는 별도로 범위를 보여준다. 백업 삭제 적용 시점도 서버 정책에 명시한다. 이미 작성된 대화 메시지와 기억 항목 삭제를 혼동하지 않는다.

원문 보존은 요약에서 누락된 정보를 다시 찾기 위해 필요하다. 반대로 요약만 계속 요약하면 출처를 잃을 수 있으므로 원문 참조를 유지하고 주기적으로 원문 기준으로 재구성한다. 오래됐다는 이유만으로 유효한 선호·합의를 자동 삭제하지 않는다.

## 목업에 반영한 것과 경계

구현된 상호작용:

- 8명 공용 에이전트의 기억과 4개 부서 공통 기억, 팀 기억, 사용자별 개인 기억.
- 사실·결정 / 경험 / 절차 / 진행 중인 약속 필터와 제목·내용·출처 검색.
- 기억 꺼내보기: 해당 에이전트가 읽을 수 있는 샘플 중 키워드로 최대 3개, 내용 합계 최대 1,800자를 선택한다. 의미 검색이나 LLM 답변은 아니다.
- 원문 발췌·출처·날짜와 이전 버전 확인. 내용 정정 시 버전 증가. 지운 항목은 검색에서 제외하고 다시 로드해도 기본 샘플로 복원하지 않는다.
- 대화의 “이 내용을 기억”과 명시적인 “기억해줘” 저장. 기억 질문에 출처 표시. 절차 기억에서 스킬 만들기로 연결.
- 기본 샘플은 다시 구성하고 변경분만 데모 상태에 저장한다. 기억을 저장 한도에 맞춰 몰래 잘라내지 않는다.

**미구현:** 실제 장기 원문 저장, 서버 권한 검사, 임베딩 검색, 자동 사실 추출·병합, 무중단 작업자, 다중 사용자 동시 갱신, 운영 백업·복구. 이 목업은 호스트 상태 저장 한도 16KiB 안에서 시연하며 한도를 넘으면 현재 화면에만 유지됨을 알린다. 장기 기억의 무제한 저장을 구현한 상태가 아니다.

- 대화 100회를 지난 뒤 과거 원문과 합의를 질문해 해당 출처를 찾을 수 있는지.
- 작업자 중단·새 대화·모델 변경 후 같은 에이전트의 기억과 작업 상태가 이어지는지.
- 개인 비서 A의 고유 내용을 사용자 B와 공용 에이전트가 검색할 수 없는지.
- 정정된 결정이 기본 검색에 우선되고 과거 버전이 현재 사실로 섞이지 않는지.
- 삭제한 기억이 검색·요약 재생성·캐시·재색인 이후 다시 나타나지 않는지.
- 부서 이동·원문 권한 철회·팀 탈퇴 후 검색 결과와 인용의 접근 권한이 갱신되는지.
- 기억이 많아져도 선택된 입력 예산과 응답 지연을 지키는지. 놓친 기억과 잘못 인용한 기억을 따로 측정하는지.
