# 팀원·팀장 화면 설계와 구현

> 2026-10-17 변경: 현재 정책·상태·Paperclip 재사용 경계·서버 복구 계약은 [리뷰 반영 확정 설계](DESIGN_IMPLEMENTATION.md)가 기준입니다. 이 문서의 기존 구조에 추가 적용합니다.

2026-10-16. 하나의 공용 팀 안에서 회원가입과 역할별 화면을 제공한다. 팀 생성·초대 코드·팀 전환은 범위에 포함하지 않는다. 실제 인증 서버나 이메일 전송은 연결하지 않는 데스크톱 프로토타입이다.

[제품 기획 검토](PRODUCT_REVIEW.md)는 현재 화면·코드에서 확인한 공개 범위·업무 조작·완료 처리와 실제 팀 사용 전 결정할 정책을 구분한다. 검토의 제안은 이 문서의 구현 정책을 변경하거나 확정한 것으로 간주하지 않는다.

## 배포별 워크스페이스

각 설치의 구성원이 하나의 워크스페이스를 사용한다. **주목표는 서버에 상주하는 직속·개발·운영·QA 공용 에이전트를 팀원들이 함께 사용하는 것**이다. 같은 공용 에이전트의 대화·업무·기억·스킬을 권한에 따라 공유하고, 다른 사람이 시작한 업무를 이어서 사용한다. 사용자별 개인 비서는 보조 기능으로 유지하며 개인 기억의 소유권을 구분한다. 회원가입은 이 공용 서비스에서 사용할 본인 계정을 준비하는 흐름이다. [공용 에이전트 제품 계약과 완료 기준](SHARED_AGENTS.md)

운영자는 팀장, 일상 사용자는 팀원으로 나눈다. 지금 제공하는 팀장 체크와 역할별 화면을 유지하며, 설치된 서비스의 로그인과 권한 부여는 서버에서 구현한다. 여러 조직을 받는 SaaS 기능이나 구독·결제는 현재 제품 범위에 추가하지 않는다.

다음 구현의 중심은 **서버의 같은 공용 Agent ID에 두 실제 사용자가 접속하고, 웹을 닫아도 업무·대화·기억·스킬과 실행 상태가 유지되는 것**이다. 로그인·공유 상태·실행 연결과 재접속 복원을 먼저 완성한다. 전체 시스템은 한 배포 단위를 기준으로 시작하고, 실행 작업자의 격리와 영속 저장은 그 안의 책임으로 구분한다.

GitHub 저장소와 Pages는 코드와 샘플 데모를 제공한다. 설치별 계정·대화·기억·파일·자격증명은 해당 운영 서버에 보관한다. Pages 데모는 브라우저의 샘플 데이터로 화면을 체험하는 용도다.

## 가입과 첫 화면

이름·이메일·소속 부서·개인 비서 이름을 입력하고 **팀장 권한을 요청할게요** 체크박스로 역할을 요청한다. 가입자는 모두 팀원으로 시작하고 공용 오피스로 이동한다. 기존 팀장이 구성원 화면에서 요청을 확인해 역할을 부여한다. 개인 비서는 두 역할 모두에게 만들어진다. 로프레는 팀장, 민지는 팀원 시연 계정이다.

실제 서비스의 관리자 권한은 조직에서 확인한 사용자에게 서버가 부여해야 한다. 체크박스 자체는 관리자 권한을 부여하지 않는다. 비밀번호·인증 키를 수집하지 않는다.

## 화면과 권한

| 기능 | 팀원 | 팀장 |
| --- | --- | --- |
| 내 업무 공간 | 나의 확인 요청·맡긴 일·결과·개인 비서·스킬 | 동일 |
| 팀 오피스·공유 대화 | 공개 범위에 맞게 이용 | 동일 |
| 개인 비서·개인 스킬 | 본인 소유만 관리 | 본인 소유만 관리 |
| 공용 동료의 역할·부서·하네스 | 이용·열람 | 설정 변경 |
| 공용 스킬 장착·게시 | 담당 스킬 게시 또는 팀 정책에 따른 편집. Agent 장착 권한은 별도 | 장착·게시와 정책 관리 |
| 팀 관리 | 메뉴 없음 | 부서별 현황·역할 요청·구성원·공용 에이전트·스킬 담당·변경 기록 |
| 다른 사람의 개인 대화·기억 | 열람 불가 | 열람 불가 |

최소 한 명의 팀장을 유지한다. 메뉴뿐 아니라 화면 진입과 변경 처리에서도 역할을 검사한다. 역할을 바꾼 결과 팀장이 아니게 되면 관리 화면을 벗어난다. 이 브라우저 정책은 서버 접근 제어를 대체하지 않는다.

## 디자인

기존 크루룸과의 연결을 위해 배경 `#faf9f7`, 패널 `#ffffff`, 본문 `#292b34`, 구분선 `#e4e3e0`, 강조 `#5956b0`, 완료색 `#20755d`를 이어 쓴다. 기존 한국어 시스템 글꼴과 제목 26px·구획 제목 17px·본문 14px·보조 정보 12px의 위계를 유지한다.

가입 화면은 왼쪽의 캐릭터 장면과 오른쪽의 간결한 양식으로 구성한다. 역할을 바꿔도 입력 내용은 유지하고, 선택한 역할로 무엇을 할 수 있는지 즉시 안내한다. 별도의 팀 설정 단계는 없다.

팀원은 왼쪽의 이어갈 업무 목록과 오른쪽의 개인 비서·스킬을 중심으로 본다. 팀장은 기존 사이드바의 **팀 관리**로 들어가 운영 현황 / 구성원·부서 / 공용 에이전트 / 스킬 담당 / 설정·기록 탭을 사용한다. 상태는 실제 시연 데이터에서 계산하며 비용·성공률 등 측정하지 않은 지표를 만들지 않는다.

위 내용은 현재 목업의 화면이다. 후속 UX의 기본 진입은 **팀 오피스 → 공용 에이전트 → 공유 대화·업무**로 잡는다. 내 업무 공간과 개인 비서는 보조 진입점으로 유지한다.

```text
가입: 캐릭터 소개 | 이름 / 이메일 / 부서 / 비서 이름 / □ 팀장 권한 요청
팀원: 공통 메뉴   | 내 확인 요청 · 맡긴 일 | 비서 · 스킬
팀장: 공통 메뉴   | 팀 관리 탭 / 부서별 현황 / 직접 편집과 변경 기록
```

1440px 기준, 1280px·1024px 데스크톱에서도 확인한다. 모바일은 범위에서 제외한다.

## 구현과 검증 기준

- 가입한 구성원과 역할·부서를 로컬 상태에 보관하고 새로고침 뒤 복원한다. 기존 스키마 8의 대화·기억·실행 기록을 유지한다.
- 가입 때 개인 비서와 비공개 첫 대화를 만든다. 역할이나 부서를 바꿔도 개인 대화 전체를 공개하지 않는다.
- 팀장 변경, 부서 추가·수정, 공용 스킬 편집 정책과 관리 이력을 제공한다. 변경 기록에 개인 대화 내용을 포함하지 않는다.
- 팀원 관리 진입 제한, 마지막 팀장 보호, 가입 중복·입력 오류, 두 역할의 가입과 복원, 개인 데이터 분리, 정책 적용을 검증한다.
- 실제 서버에서는 가입자 인증, 팀장 승인·부여, API와 파일·이벤트의 권한 강제, 동시 변경과 감사 기록을 별도로 구현해야 한다.

`state.members`에는 사용자 ID·이름·이메일·역할·부서를, `state.team`에는 이름·소개·부서·공용 스킬 편집 정책·최근 100개의 관리 기록을 보관한다. 역할이 바뀌어도 개인 비서의 ID와 기억은 바꾸지 않는다. 기록에는 동작과 대상만 남기고 개인 메시지 본문은 넣지 않는다.

가입 폼의 초안과 현재 관리 탭도 복원한다. 전체 상태는 동일 브라우저의 localStorage에 함께 저장되므로 개발자 도구 접근을 막는 보안 경계는 아니다. 관리 기록도 위변조를 막는 서버 감사 로그가 아니다.
