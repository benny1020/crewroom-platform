# 크루룸 · 제품 기획 검토

> 이 문서는 당시 리뷰 기록입니다. 사용자 승인 후 반영한 현재 정책·화면·미구현 서버 조건은 [리뷰 반영 설계와 추적표](DESIGN_IMPLEMENTATION.md)를 참고하세요.

2026-10-16. 검토 대상은 당시의 웹 프로토타입과 기획 문서다. 아래 파일·행 참조는 당시 검토 위치이며 현재 동작을 뜻하지 않는다. 코드, 기존 화면 캡처, 공개 데모의 실제 조작을 함께 확인했다. 아래 **제안은 아직 합의하거나 구현한 정책이 아니다.** 이번 검토에서는 앱의 동작을 변경하지 않았다.

## 판단

**제품 목표:** 서버에 상주하는 공용 에이전트를 워크스페이스 구성원이 함께 사용한다. 개인 비서는 보조 기능이다. [공용 에이전트 제품 계약](SHARED_AGENTS.md)을 우선 기준으로 적용하며, 아래 정책 보완 제안과 구분한다.

**해결할 문제:** 개별 스킬·개별 세션으로 인한 공유 단절과 결과물 형식 차이를 해결한다. 이 목적에서 가장 중요한 공용 스킬 버전·업무별 공유 세션·결과 검증·산출물 저장의 빈틈은 [표준화 이슈 검토](TEAM_STANDARDIZATION_REVIEW.md)에 현재 코드 근거와 통과 기준으로 정리했다. 아래 다섯 정책과 함께 적용해야 한다.

**제품의 방향과 화면 구조는 시연하기에 충분히 구체적이다. 실제로 팀 업무를 맡길 MVP의 기획은 아직 닫히지 않았다.** 부족한 부분은 메뉴나 에이전트 수보다 공개 범위, 업무 책임, 완료 판정, 실패 이후의 행동이다. 이 규칙이 먼저 정해져야 서버 구현과 화면이 같은 제품을 가리킨다.

현재 확인한 것은 로컬 저장·샘플 실행을 사용하는 프로토타입이다. 실제 다중 사용자, 외부 도구, 장기 운영, 사용자 대상 사용성 검증을 입증한 것은 아니다. 기존 도메인 13건·브라우저 시나리오 23건도 해당 구현의 회귀 검사이며, 제품 기획 전체의 완성도 점수가 아니다. 이번 검토의 로컬 확인은 화면 조작·코드 검토·문서 검증이며 전체 회귀 검사를 다시 실행하지는 않았다.

## 실무 효용 재검토

2026-10-16. **크루룸은 팀이 함께 쓰는 AI 업무 공간으로 목적에 맞지만, 현재는 실제로 일을 맡길 수 있는 AI 팀이 아니다.** 공용 서버·실행기·다중 사용자 동기화가 없는 목업이므로 실제 성과는 아직 측정하지 않았다.

효용의 중심은 개인 세션마다 반복하던 설명·설정·인계·보고서 편집을 줄이는 데 있다. 부서별 캐릭터는 담당과 상태를 찾는 진입점이고, 실제 가치는 공용 스킬 버전·업무별 공유 세션·검증 근거·검색 가능한 결과물에서 나온다. 에이전트 수가 늘어나는 것 자체는 성과로 세지 않는다.

첫 구현은 한 프로젝트의 **PR 검토 → QA 인계** 한 흐름으로 시작하는 것이 적절하다. 개발 에이전트가 대상 커밋과 변경 근거를 남기고 QA 에이전트가 그 결과를 검증 범위·재현 절차로 이어받는다. 실제 도구로 확인한 내용과 제안·미확인 항목을 구분하고, 두 팀원이 같은 업무방에서 맥락과 결과를 이어갈 수 있어야 한다. 일반적인 팀원 역할 전체를 자율 수행한다고 약속할 단계는 아니다.

### 검증할 결과

| 기준 | 측정 방법 | 유용하다고 볼 근거 |
| --- | --- | --- |
| 사람의 총 작업 시간 | 준비·지시·검토·재작성·실패 복구 시간을 합해 기존 방식과 비교 | 검토와 복구까지 포함해 반복 업무의 부담이 줄어듦 |
| 인계의 연속성 | 다른 팀원이 원문·결과·다음 행동을 찾아 이어가는 장면 관찰 | 배경 설명을 처음부터 다시 듣지 않아도 이어갈 수 있음 |
| 결과 품질과 표준 | 사실·코드 근거·검증 범위를 내용 검토하고 형식 검사를 별도로 수행 | 같은 양식으로 나온 오류를 성공으로 세지 않음 |
| 운영 부담과 재사용 | 실행 비용·대기·실패·수정량, 같은 업무의 재사용 여부 기록 | 관리하는 수고가 절감 효과를 상쇄하지 않음 |

같은 유형과 난이도의 실제 업무를 기존 방식과 시범 방식으로 비교하고 표본 수·대상 버전을 남긴다. 합격 수치는 측정 전 팀이 정하며, 현재 절감률이나 생산성 향상 수치는 없다. 첫 흐름이 유용하다는 근거를 확보한 다음 운영 점검·주간 정리로 넓힌다. 개인 비서 확대나 추가 프레임워크 도입은 이 검증의 선행 조건이 아니다.

## 유지할 결정

- **설치마다 독립 워크스페이스 하나**를 제공한다. 새 팀 생성·초대 코드·조직 전환·구독·결제·모바일을 추가하지 않는다.
- 직속·개발·운영·QA 아래 공용 에이전트를 두고, 모든 구성원에게 개인 비서를 제공한다. 팀장도 다른 사람의 개인 대화·기억을 열람하지 않는 원칙을 유지한다.
- 에이전트, 대화, 업무(Task), 실행(Run)을 구분한다. 같은 에이전트에게 여러 업무를 맡기더라도 각각의 결과와 이력이 남아야 한다.
- 스킬의 적용 버전, 기억의 출처·정정, 재개 기록을 사용자에게 설명하는 방향을 유지한다.
- 캐릭터와 모션을 유지하면서 업무·대기 이유·결과로 바로 이어지게 한다. 팀원 홈과 팀장 관리 화면을 나눈 것도 적절하다.

### P0-1. 공개 범위를 하나의 규칙으로 맞춘다

**확인한 동작:** 공용 에이전트와의 비공개 대화에서 `이 요청으로 업무 맡기기`를 누르면 `팀 업무로 공유하기`가 기본 선택된다. 양식을 확인해 제출한 요청 문장은 팀 공유 업무가 되고 다른 시연 구성원에게 보인다. 개인 대화 전체가 자동 공유된 것은 아니며, 공유 체크가 보이는 확인 양식을 거쳤다. 다만 비공개 맥락에서 출발한 사용자가 기본값을 그대로 받아들이기 쉽다. 양식 기본값 (`src/app.js:1860`, 당시 검토) · 업무 생성 (`src/app.js:2174`, 당시 검토)

또한 부서 대화는 사용자의 소속을 확인하지만, 기억 화면은 선택한 에이전트의 부서 기억을 보여 준다. QA 구성원 민지가 개발 에이전트의 `인증 오류 처리 계약` 기억을 볼 수 있었다. `부서 공통`이 분류인지 접근 제한인지 기획상 의미가 다르다. 대화 열람 조건 (`src/domain.js:26`, 당시 검토) · 기억 열람 조건 (`src/app.js:198`, 당시 검토)

**제안:** 대화에서 파생한 업무는 원본의 공개 범위를 기본으로 상속한다. 팀에 공유할 때 요청·결과·첨부 중 공유될 내용을 미리 보여 주고 별도 공개본을 만든다. 개인 비서가 수행한 업무도 결과 일부만 팀에 보낼 수 있게 한다. 팀장은 공유본을 볼 수 있어도 개인 원문을 따라 들어갈 수 없다.

부서는 우선 조직 탐색과 자료 분류로 쓰고, 공통 업무 지침은 `개발 참고자료 · 팀 공유`처럼 표시하는 방식을 권한다. 실제로 부서 비공개 자료가 필요하다면 현재의 부서 범위를 유지하고 대화·기억·검색·첨부·결과에 같은 열람 규칙을 적용해야 한다. **부서 비공개를 없애기로 결정한 것은 아니다.**

**통과 조건:** 비공개 대화 → 업무 → 결과 → 기억 → 검색·알림까지 의도하지 않은 범위 확대가 없다. 공개본의 비공개 출처는 다른 사람에게 노출되지 않는다. 부서 변경이나 계정 전환 뒤에도 같은 규칙으로 판단된다.

### P0-2. 공유 업무에도 사람 책임자가 필요하다

**확인한 동작:** 로프레가 만든 공유 업무를 민지로 전환해 재개하고 정지할 수 있었다. 현재 `taskBy`는 열람 가능한 업무를 반환하고, 실행 조작은 요청자와 열람자를 별도로 구분하지 않는다. 입력 대기 양식의 답변 처리도 같은 조회를 사용한다. 업무 조회 (`src/app.js:332`, 당시 검토) · 실행 조작 (`src/app.js:2506`, 당시 검토) · 대기 중 답변 (`src/app.js:3073`, 당시 검토)

이는 팀원 간 협업을 허용한 시연으로 볼 수도 있다. 그러나 실제 업무에서 누가 답할지, 충돌하는 답변 중 무엇을 적용할지, 누가 중단에 책임질지가 정해지지 않았다. `내 답변 대기`는 단순히 볼 수 있는 대기 업무와 달라야 한다.

**제안:** 계정 역할은 팀장·팀원 두 개로 유지하고, 업무마다 요청자와 현재 사람 책임자를 둔다. 특별히 지정하지 않으면 요청자가 책임자가 된다. 외부 도구 승인은 해당 도구 권한을 가진 승인자에게 별도로 요청한다.

| 관계                    | 제안하는 기본 행동                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------- |
| 공유 업무 열람자        | 읽기·댓글·업무 인수 요청                                                            |
| 요청자 또는 현재 책임자 | 범위 답변·일시정지·재개·중단·결과 확인·재작업 요청                                  |
| 팀장                    | 공유 업무 책임자 재배정·긴급 중단. 본인 개입임을 기록                               |
| 외부 도구 승인자        | 구체적인 대상과 변경 내용에 대한 승인. 팀장 여부만으로 모든 계정의 권한을 얻지 않음 |

위 표는 제안이다. 작은 팀이 모든 공유 업무의 공동 조작을 원한다면 그 정책도 가능하지만, 조작자 표시와 충돌 처리까지 명시해야 한다. 개인 업무에는 팀장의 공유 업무 개입 권한을 확장하지 않는다.

**통과 조건:** 같은 확인 요청에 두 사람이 답해도 한 번만 적용된다. 확인 요청은 담당자의 수신함에 나타나며 담당·인수 이력이 남는다. 권한 없는 조작은 버튼과 서버 처리 양쪽에서 거부된다.

### P0-3. 실행 종료와 업무 완료를 구분한다

**확인한 동작:** `finish`는 샘플 흐름이 끝나면 Task를 바로 `done`으로 바꾸고 정해진 예시 결과를 보여 준다. 결과에는 시연임을 밝히고 있어 실제 검증 결과로 속이지는 않는다. 그러나 실제 제품에서 결과를 받아들이거나 재작업하는 계약은 아직 구체적이지 않다. 완료 처리 (`src/app.js:2066`, 당시 검토) · 결과 화면 (`src/app.js:1352`, 당시 검토)

**제안:** 실행 성공은 `결과 준비`를 뜻한다. Task의 완료 기준은 업무마다 정한다. 초안 생성, 검증 통과, 저장소 반영, 배포 완료를 각각 정확한 말로 표시한다. 모든 요약에 사람의 승인을 강제하지 않고, 코드 변경·외부 반영처럼 확인이 필요한 업무에 검토 단계를 둔다.

결과 화면의 공통 계약은 **산출물 링크 / 요청한 완료 기준별 근거 / 아직 확인하지 않은 것 / 다음 행동**이다. 재작업은 같은 업무 안에서 이유와 결과 버전을 유지하고 새 Run으로 진행한다. 과거 실패나 결과를 덮어쓰지 않는다.

**통과 조건:** 수정안만 만들었으면 `배포 완료`가 되지 않는다. QA 보고서는 확인한 환경·범위·대상 버전을 가진다. 사용자는 결과를 수용하거나 이유를 남겨 재작업을 요청할 수 있다.

### P0-4. 실패와 대기의 주체·행동을 정한다

**현재 상태:** 목업에는 접수·진행·입력 대기·정지·완료·취소가 있다. 아키텍처 문서에는 복구 관련 제안이 있지만, 권한 만료·실행 실패·응답 없음·예산 소진 등을 사용자가 어떻게 처리하는지 화면 계약은 더 필요하다.

**제안:** 다음 네 가지를 항상 답할 수 있게 한다. `어디까지 했는가 / 왜 멈췄는가 / 누가 무엇을 해야 하는가 / 다시 시작하면 무엇을 반복하는가`.

| 상황                | 보여 줄 내용과 다음 행동                                                 |
| ------------------- | ------------------------------------------------------------------------ |
| 사용자 정보 부족    | 질문·필요한 입력·답할 사람·답변 후 이어질 단계                           |
| 도구 연결·권한 만료 | 연결할 서비스·영향받는 업무·연결을 복구할 사람                           |
| 실행 실패·한도 도달 | 마지막 성공 단계·남은 산출물·원인·재시도 또는 범위 축소                  |
| 외부 변경 결과 불명 | 이미 적용됐는지 확인 중임을 표시. 확인 전 같은 변경을 다시 요청하지 않음 |
| 정지·중단 요청      | 새 행동을 멈추는 시점·진행 중 도구의 종료 여부·이미 반영된 변경          |

**통과 조건:** 브라우저를 닫아도 서버 작업의 상태를 다시 확인할 수 있다. 재시도 시 외부 변경이 중복되지 않는다. `중단`이 이미 보낸 메시지나 반영된 변경을 자동 취소한다는 인상을 주지 않는다. 정상 완료, 중간 입력, 실패, 연결 끊김을 각각 실제 사용 흐름으로 검증한다.

### P0-5. 워크스페이스 가입·팀장 권한의 부여 절차를 정한다

**현재 상태:** 가입 화면의 `팀장이에요` 체크는 즉시 목업 역할이 된다. [현재 문서](TEAM_WORKSPACE.md#가입과-첫-화면)는 실제 권한을 서버에서 부여해야 한다고 명시한다. 필요한 방향은 이미 있으나 첫 팀장과 후속 가입자의 권한을 어떻게 확인할지는 미정이다.

**제안:** 가입 체크는 유지하되 실제 서비스에서는 역할 요청으로 취급한다. 첫 팀장은 배포 설정에 등록한 계정으로 시작하고, 이후 서버가 확인한 팀 구성원에게만 계정을 연결한다. 추가 팀장 권한은 기존 팀장이 부여한다. 초대 코드나 새 팀 생성 없이 운영할 수 있다. 통합 로그인 또는 허용 계정 목록 중 팀 환경에 맞는 방식을 선택해야 한다.

**통과 조건:** 임의의 가입자가 팀장 체크만으로 관리자 권한을 얻지 않는다. 마지막 팀장 보호가 서버에도 적용된다. 접근 중지된 사람은 새 실행을 시작하거나 이전 연결을 사용할 수 없다.

## 사용성을 더 좋아지게 만드는 역할 분담

개인 비서·공용 동료·스킬 중 어디에서 시작해야 하는지 학습해야 한다면 캐릭터의 친근함이 실제 편의로 이어지기 어렵다.

**주목표에 맞춘 기본 흐름:** 팀 오피스에서 공용 에이전트를 선택한다 → 권한이 있는 공유 대화·업무에 참여하거나 새 업무를 맡긴다 → 서버가 수행하는 상태와 확인 요청을 함께 본다 → 같은 업무에서 맥락과 결과를 이어간다. 스킬은 해당 공용 에이전트에서 바로 실행하고, 내 업무 공간과 개인 비서는 보조 진입점으로 둔다. 앞선 개인 비서 우선 진입 제안은 이 흐름으로 대체한다. 현재 목업 화면을 변경한 것은 아니다.

| 화면            | 가장 먼저 답할 질문                                                |
| --------------- | ------------------------------------------------------------------ |
| 내 업무 공간    | 오늘 내가 답할 것과 준비된 결과는 무엇인가?                        |
| 내 비서         | 이전 맥락을 이어서 무엇을 맡길 수 있는가?                          |
| 부서별 에이전트 | 누가 이 업무를 잘하고, 어떤 도구를 쓸 수 있는가?                   |
| 팀 오피스       | 어디가 진행 중이고 무엇이 막혔으며 언제 갱신됐는가?                |
| 업무 상세       | 대상·책임자·공개 범위·산출물·다음 행동은 무엇인가?                 |
| 팀 관리         | 어떤 공유 업무에 개입해야 하고, 누가 연결·정책을 복구할 수 있는가? |

캐릭터를 눌렀을 때 업무와 이유를 보여 주는 현재 방향은 유지한다. 모션만으로 성공·집중도·성과를 추정하게 만들지 않는다. 개인 비서의 커스텀은 이름·말투·기억·자주 쓰는 스킬부터 제공하고, 하네스·실행기 선택은 필요한 사람의 고급 설정에 둔다.

## P1 · 첫 시범 운영에서 필요한 운영 기획

| 항목              | 보완할 결정                                                                                                | 검증할 장면                                                                                  |
| ----------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 동시 업무         | 공용 에이전트의 정체성과 각 업무의 실행 맥락을 분리. 같은 업무의 변경은 순서대로 처리하고 별개 업무는 격리 | 두 팀원이 같은 에이전트에게 요청해도 입력·결과·개인 기억이 섞이지 않음                       |
| 오피스의 진실성   | 현재 화면은 에이전트별 대표 업무 하나를 선택함. 다른 진행 건수·대기열·마지막 서버 갱신 시각도 필요         | 대표 업무 외에 진행 중인 건수를 알고, 연결이 끊기면 갱신 중단으로 표시                       |
| 대화 중 추가 지시 | 댓글·후속 지시·현재 실행에 적용된 입력을 구분. 진행 중 범위 변경은 적용 시점과 새 실행 필요 여부를 안내    | 댓글이 단순 기록인지 에이전트가 접수한 변경인지 알 수 있음                                   |
| 기억 품질         | 오래 보관하는 것과 정확히 꺼내 쓰는 것을 분리. 출처·유효 시점·충돌·정정·삭제의 사용자 의미 확정            | 옛 결정과 새 결정이 충돌하면 최신 유효 근거를 설명하고, 근거가 없으면 모른다고 답함          |
| 기억에서 스킬로   | 반복 행동은 스킬 초안으로 제안하고 시험 실행 후 사람이 공용 게시                                           | 실패한 절차가 공통 규칙이 되지 않음. 개인 초안 → 예시 입력 검증 → 공용 게시 → 이전 버전 복구 |
| 스킬 책임         | 소유자·입력·산출물 예시·사용 도구·버전·변경 이유를 묶음. 진행 Run은 고정 버전 유지                         | 개정이 진행 중 실행을 바꾸지 않고 다음 실행에만 반영                                         |
| 알림              | 답할 사람에게 질문·실패·결과 준비를 전달하고 읽음과 처리 완료를 구분                                       | 답변 후 중복 알림이 사라지고 담당자 변경 시 수신 대상도 변경                                 |
| 팀장 운영         | 막힌 업무·오래 기다린 확인·연결 실패·반복 재시도·실행 한도에 집중                                          | 작업 중 캐릭터 수 외에 개입 이유와 직접 연결되는 행동이 보임                                 |
| 계정·연결 종료    | 접근 중지 시 새 실행 차단·연결 해제·진행 업무 재배정. 공용 기록 보존과 개인 기록 열람은 별개               | 공유 업무는 이어가되 개인 원문이 팀장에게 열리지 않음                                        |
| 실행 한도         | 업무별 시간·단계·비용 상한과 팀 전체 사용량의 처리 방식. 워크스페이스 운영 정책                               | 한도에서 멈추면 지금까지의 결과·남은 범위·재개 판단 근거를 제공                              |
| 도구 상태         | 실제 가능한 행동을 `저장소 읽기 연결됨 / 테스트 환경 미연결 / 쓰기는 승인 필요`처럼 표시                   | 미연결 기능을 완료했다고 말하지 않고 필요한 연결 또는 가능한 대안을 안내                     |

장기 기억의 저장·검색 방향은 [기존 설계](MEMORY_ARCHITECTURE.md)에 있다. 정정과 삭제가 원문·요약·검색 결과 중 어디에 적용됐는지 사용자가 확인할 수 있게 보완한다. 보존 기간과 비용 한도는 실제 팀 요구에 맞춰 정해야 하며 임의의 기간을 제품 정책으로 확정하지 않는다.

## 첫 실제 업무는 세 가지로 검증한다

아래는 우선 검증할 **후보**다. 실제 팀의 빈도와 소요 시간을 확인한 뒤 선택해야 한다. 새로운 부서·에이전트·실행 프레임워크를 추가할 이유는 아니다.

| 후보                    | 입력                            | 유용한 결과의 기준                                                       |
| ----------------------- | ------------------------------- | ------------------------------------------------------------------------ |
| PR 변경 요약·검토       | 저장소·PR·기준 커밋·검토 범위   | 변경 위치와 근거가 연결되고 실제 실행한 검사와 미실행 검사를 구분        |
| 변경 사항에서 QA로 인계 | 요구 사항·변경 버전·테스트 환경 | 재현 절차·예상 결과·검증 범위가 있고 개발→QA→사람 책임자의 인계가 이어짐 |
| 주간 업무 정리          | 선택 기간·공유 업무·산출물      | 출처가 있는 요약, 완료·결과 준비·막힘 구분, 개인 대화 미포함             |

첫 사용은 프로필 설정 완료로 끝내지 않고 실제 자료로 첫 유용한 결과를 받는 데까지 이어져야 한다. 사용할 수 없는 연결은 시작 전에 알린다. 팀원이 끝난 결과를 손으로 얼마나 고쳤는지도 확인한다.

## 다음 단계의 완료 기준

1. 다섯 P0 정책을 업무 양식·확인 요청·결과·공유·팀장 화면의 같은 용어로 표현한다.
2. 실제 한 팀의 계정과 저장소를 연결하고 선택한 반복 업무를 처음부터 결과 확인까지 수행한다.
3. 서로 다른 두 계정·브라우저에서 같은 업무와 다른 업무를 동시에 처리한다. 시연 사용자 전환만으로 동시 사용 검증을 대신하지 않는다.
4. 정상 종료·재작업·입력 대기·권한 만료·실행 실패·중단·재개를 확인하고 산출물과 조작 이력을 남긴다.
5. 개인·공유·부서 범위의 대표 사례를 대화·업무·기억·검색·첨부·알림에서 확인한다. 원치 않은 공개와 외부 변경 중복이 있으면 사용 범위 확대를 멈추고 원인을 고친다.
6. 팀원에게 설명 없이 업무를 맡기게 하고 첫 유용한 결과까지 걸린 시간·수정에 든 노력·반복 사용 여부·실행 시간과 비용을 기록한다. 합격 수치는 현재 측정값이 없으므로 시범 사용 전에 합의한다.

기획의 다음 우선순위는 **하나의 실제 업무를 공동으로 끝내는 흐름**이다. 한 배포·공유 저장소·교체 가능한 실행기라는 기존 방향 안에서 진행할 수 있다. 이 검토만으로 프레임워크를 다시 선정하거나 서비스를 여러 개로 분리하지 않는다.

| 확인 방법           | 확인한 내용                                                             | 입증하지 않은 내용                                |
| ------------------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| 고정 커밋 코드·문서 | 상태·공개 범위·역할 검사·결과 처리와 기획의 대응                        | 실제 서버의 권한·인증·복구 구현                   |
| 공개 데모 실제 조작 | 비공개 대화 → 공유 기본값 → 제출 → 다른 시연 구성원의 요청 열람         | 확인 없이 대화 전체가 자동 공개된다는 주장        |
